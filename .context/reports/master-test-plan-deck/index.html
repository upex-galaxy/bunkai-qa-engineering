Master Test Plan · Resumen ejecutivo

Las zonas frágiles
no son las pantallas —
son auth, credenciales y aislamiento multi-tenant

Bunkai TMS es un sistema cuyo producto es la corrección y la trazabilidad. Casi toda la autorización real vive dentro de RLS en Postgres, alcanzada por 4 helpers SECURITY DEFINER. Una regresión de RLS es una brecha, no un glitch — y es invisible desde la UI.

El moat de anclaje ES la propuesta de valor

Cada ATC debe enlazar a una User Story y ≥1 Acceptance Criterion (INV-1, INV-2). Un bug que deja existir un ATC sin Story no es cosmético: es un hueco en lo que el cliente paga. Trátalo como un cálculo de saldo en un banco.

Apertura: el reflejo es testear las pantallas, pero el riesgo está en la frontera de autorización y la fontanería de credenciales. Subrayar que RLS = seguridad, no detalle. Y que el anclaje ATC→Story→AC es el diferenciador del producto.

3 CRÍTICOS · 4 ALTOS

Lo más frágil no es la lógica de negocio — es la puerta de entrada y el plano de credenciales.

CRITICAL · Flow A / A'

Auth gateway

Magic-link + headless. Si cae el login, el producto entero es inalcanzable. Puerta a todos los flujos.

CRITICAL · Flow F

Aislamiento tenant + secretos

Fuga entre workspaces (INV-3) o exposición de hashes de credenciales (INV-11) = brecha multi-tenant.

CRITICAL · Flow D / E

PAT + Bearer

Emisión de credenciales. Scope sin aplicar = escalada de privilegios silenciosa.

ALTOS (4)

ATC authoring (Flow B, bunkai_save_atc) — el trabajo central del producto · Workspace bootstrap (FEAT-003) — sin él, el usuario nuevo queda varado · Invitaciones (Flow C) — superficie de escalada de privilegios · Árbol de módulos (FEAT-011) — path materializado en app, sin trigger.

El agujero más caro de cerrar

Los scopes de PAT no se aplican

# control de scope de PAT — grep repo-wide

requireScopeOrCookie()    ← definido
  llamado en:  0 endpoints

# consecuencia (INV-4 solo se valida al emitir, nunca al usar):
PAT(atc:read)   ==   PAT(workspace:admin)

# además — Bearer anunciado en spec vs implementado:
spec OpenAPI:  bearerAuth en 11 operaciones
real en codigo: 2  (GET /api/v1/me, GET /api/v1/workspaces)

Drift spec ↔ implementación

Las otras 9 operaciones son cookie-only → devuelven 401 a un caller solo-Bearer, contradiciendo el contrato publicado. Sin verificar si es aspiracional o bug — confírmalo antes de escribir los contract tests.

finding · pat scope gap03 / 08
Este es el test de más valor: emitir un PAT solo atc:read e intentar una escritura/admin. Hoy se espera que pase (= defecto), captúralo como bug, no como pass. Es escalada de privilegios latente.
silent killers · 704 / 08

Lo que se pudre sin avisar

Procesos automáticos sin camino de feedback. Casi siempre el área menos testeada.

!
modules.path — materializado en código de app, sin trigger en DB. Un move que olvida recomputar deja el árbol roto, sin señal.
!
atcs_refresh_tsv — si el trigger deja de disparar, la búsqueda de ATC devuelve vacío en silencio; el usuario cree que perdió datos.
!
Resend declarado, NO conectado — los emails de invitación nunca se envían. Parece OK; no lo está (URL por clipboard/stdout).
!
Run-execution NO existe — ningún proceso mueve atcs.status. Probar "ejecuta y mira el estado" = testear vapor.
!
Sin CI/CD — .github/workflows vacío, sin gate de test/lint antes de prod. Cada regresión llega a producción callada.
!
.env desde .env.example — arranca en "Invalid environment variables" (key legacy vs nuevas). Trampa de primer arranque, real, no hipotética.
silent killers · no feedback path04 / 08
Estrategia QA para silent killers: probes sintéticos (crear ATC → buscarlo), auditorías de integridad programadas (modules.path vs cadena de padres), y aserciones de log. El gate CI/CD es el arreglo de proceso de mayor palanca.

Testea los helpers, no solo las pantallas

Si el bootstrap medio-falla (workspace creado, owner no inscrito), el authoring parecerá disponible pero toda escritura falla en RLS — una rotura que solo aparece después del login.

cascade · isolation hides breakage05 / 08
Tercera cadena: precedencia de token — requireAuth chequea Bearer primero, así una cookie stale no eclipsa un PAT explícito. Probar el caso con ambas credenciales presentes, no una a una.
