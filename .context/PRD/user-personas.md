## Persona 1 — Elena Vargas (Senior QA Engineer)

**The protagonist user. The framework's tests primarily simulate Elena.**

| Attribute | Value |
|---|---|
| Age / Location | 36, Buenos Aires (remote) |
| Education | Computer Science + 12+ yrs testing, ISTQB Advanced |
| Tech savviness | Early adopter; VS Code + Chromium DevTools; `git`; basic SQL / JavaScript / YAML / Bash; Playwright + Cypress |
| **Bunkai role** | `member` or `admin` (RBAC); occasionally PAT holder with `atc:read`, `atc:write`, `run:execute` |

### Goals

1. Cover regression without rewriting tests every release.
2. Make traceability provable on demand (US → AC → ATC → Run → Bug).
3. Shift left — catch ambiguity in ACs before dev starts.
4. Delegate routine execution to AI agents (Karim) so she focuses on exploratory + high-value test design.

### Frustrations / pain points

- Duplication in Xray: a "login" step lives in 40 separate tests; URL change is a 40-file edit.
- Reports lie: "80% passing" tells the PM nothing about what's actually covered.
- Bugs lost in translation: handing off to Jira loses Module / ATC / Run context.
- Tools work *against* her process — she has to bend the TMS to enforce structure manually.

### Quote (verbatim)

> *"No me molesta escribir tests. Me molesta tener que reescribirlos cada release porque el TMS no entiende que el login es un ATC, no un párrafo copiado 40 veces."*

Source: `<target>/.context/PRD/user-personas.md` (Persona 1).

### QA framework implications

- **E2E coverage**: Elena's UI flows (sign-in, create Project, create Module tree, author ATC, chain Test, run Test, file Bug) are the **primary smoke + regression suite** the framework must own.
- **Performance budget**: command palette (Cmd+K) must respond <100ms in tests against staging.
- **Accessibility**: Elena uses keyboard shortcuts (`P` / `F` / `B` for pass/fail/block during runs) — keyboard-only E2E paths required.

## Persona 4 — Karim (Autonomous AI Test Agent — non-human)

**The API-first consumer. The framework's API tests simulate Karim directly.**

| Attribute | Value |
|---|---|
| Identity | Not a person; an AI agent (Claude Code, Playwright-driven harness, or bespoke agent) |
| **Bunkai role** | PAT holder with explicit scope set; **no UI session** |
| Typical scope set | `atc:read` (always) + `run:execute` (to record outcomes) + sometimes `atc:write` (to log bugs as new ATCs) |
| Token storage | `bk_pat_<prefix>.<secret>` format; SHA-256 hashed at rest in `access_tokens.hash` |

### Goals

1. Receive a Test as a structured payload (JSON, not natural-language steps).
2. Drive the app under test and report step-by-step.
3. Mark `pass / fail / blocked` in real-time on the Run.
4. Open Bugs with auto-populated context (Module, ATC, Run, env, evidence URLs).

### Frustrations / pain points (AI-agent specific)

- APIs fight back: inconsistent error shapes, no idempotency keys, hidden state.
- No write-back primitive — many TMSs assume humans only.
- Auth complexity — OAuth flows are hostile to headless agents.

### Technical expectations

- OpenAPI 3.x spec (Karim consumes the contract directly).
- Bearer-token auth via `Authorization: Bearer bk_pat_…`.
- WebSocket / SSE channel for real-time Run updates (Supabase Realtime — leveraged).
- **Idempotency keys** on `POST /api/v1/runs` so retries don't duplicate.
- Predictable response shapes (Zod-derived schemas → OpenAPI).
- Stable semver API (`/api/v1/*` is the contract surface).

### Quote (verbatim)

> *"Give me a deterministic API. I will give you a test runner."*

Source: `<target>/.context/PRD/user-personas.md` (Persona 4).

### QA framework implications

- **API test suite is Karim's mirror image**: every endpoint Karim consumes must have an ATC at `layer: API` in the framework.
- **Idempotency tests**: `POST /api/v1/runs` with the same idempotency key must return the same Run on retry — this is a P0 contract test.
- **Bearer auth tests**: valid PAT / expired PAT / revoked PAT / wrong-scope PAT — four contract paths per protected endpoint.
- **Scope-grain tests**: a PAT with only `atc:read` must get `403` on `atc:write` endpoints; the framework must own a scope-coverage matrix.

## RBAC matrix (cross-persona view)

| Action | Viewer | Member | Admin | Owner | PAT scope needed |
|---|---|---|---|---|---|
| List workspaces (own) | ✅ | ✅ | ✅ | ✅ | session OR any PAT |
| List ATCs in a project | ✅ | ✅ | ✅ | ✅ | `atc:read` |
| Create / update ATC | ❌ | ✅ | ✅ | ✅ | `atc:write` |
| Record Run result | ❌ | ✅ | ✅ | ✅ | `run:execute` |
| Invite member | ❌ | ❌ | ✅ | ✅ | `workspace:admin` |
| Change workspace plan / delete workspace | ❌ | ❌ | ❌ | ✅ | `workspace:admin` (owner only at DB level) |

Source: RBAC enforced by RLS policies in `0001_tenancy.sql` + helpers in `0005_rls_helpers.sql` (`bunkai_is_workspace_member`, `bunkai_can_write_workspace`, `bunkai_is_workspace_admin`, `bunkai_is_workspace_owner`). PAT scope CHECK constraint in `0008_access_tokens.sql`.
