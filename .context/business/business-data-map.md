## 1. Executive summary

Bunkai TMS is an open-core, multi-tenant Test Management System. A **Workspace** is the tenant boundary; it owns **Projects**, each Project owns a depth-capped tree of **Modules**, Modules own **User Stories**, Stories decompose into ordered **Acceptance Criteria**, and the core asset — the **ATC (Acceptance Test Case)** — anchors to a Project + Module + Story and binds to one or more Acceptance Criteria through an M:N join. That mandatory binding is the product's whole reason to exist: it makes "untraceable test cases" structurally impossible, so coverage and traceability are guaranteed by the schema rather than by team discipline.

Two populations use the system. **Humans** (QA engineers, QA leads, developers) sign in passwordlessly via Supabase magic-link and work through the web UI; their authorization is governed entirely by Postgres Row-Level Security keyed to their workspace membership and role. **Machines** (CLI tools and AI agents such as the persona "Karim") authenticate with **Personal Access Tokens (PATs)** — `bk_pat_…` bearer tokens carrying a scoped permission set — so non-interactive consumers can read and write test assets without a browser session. As of this refresh the Bearer-PAT path is fully wired on the two introspection/listing endpoints (`GET /api/v1/me`, `GET /api/v1/workspaces`), and PATs can now be minted headlessly in a single sign-in/sign-up call.

The value proposition is **enforced traceability + agent-readiness**: a workspace owner can invite teammates by email, organize an application-under-test into a module tree, author richly-structured ATCs (markdown steps + YAML assertions) that cannot be saved unless they are anchored, and hand an AI agent a scoped token to consume the same data over a documented REST API. The newest engineering theme is **secret hygiene**: token, invite, and magic-link secret hashes have been moved out of their main tables into service-role-only sibling tables so that read-only QA/analytics database roles can inspect operational data without ever seeing a credential hash.

```
                         WHO TOUCHES THE SYSTEM
  +-------------------------------------------------------------------+
  |  HUMANS (magic-link session, RLS-governed)                        |
  |    Owner ........ creates workspace, renames/deletes it, invites  |
  |    Admin ........ invites/revokes members, manages invites        |
  |    Member ....... authors projects/modules/stories/ACs/ATCs       |
  |    Viewer ....... read-only                                       |
  +-------------------------------------------------------------------+
  |  MACHINES (PAT bearer, scope-governed)                            |

  |    Auth ......... issues magic-link OTP, mints/refreshes session  |
```

| Entity | Business role | Why it exists |
|---|---|---|
| `workspaces` | The tenant | Top-level ownership boundary; every downstream row resolves its tenant by walking back to a `workspace_id`. |
| `workspace_members` | RBAC membership | Joins a user to a workspace with a role + status; the authorization backbone every RLS policy probes. |
| `projects` | Application-under-test | The unit a team organizes its test assets around (one app = one project). |
| `modules` | Feature-area tree | Hierarchical scope (`auth/login/mfa`); depth capped at 6 to bound tree-view queries. |
| `user_stories` | Unit of business intent | Carries requirements; optionally links out to an external tracker (Jira) via `external_id`/`external_url`. |
| `acceptance_criteria` | Testable criterion | What an ATC must verify; the anchoring target. |
| `atcs` | **The core asset** | The Acceptance Test Case — the thing the whole schema exists to organize, version, search and execute. |
| `atc_steps` | Manual execution steps | Ordered "what to do" for a tester (authored as markdown). |
| `atc_assertions` | Expected outcomes | Ordered "what must be true" (authored as YAML). |
| `atc_acceptance_criteria` | The anchoring moat | M:N link enforcing "every ATC verifies >= 1 AC". |
| `access_tokens` | Personal Access Token | Lets CLI/AI consumers authenticate without a session; scoped + soft-revocable. |
| `access_token_secrets` | Isolated PAT hash | **NEW (0011)** — holds the SHA-256 hash alone, in a table only `service_role` can read. |
| `workspace_invites` | Teammate invitation | **NEW (0010)** — email + role invite an owner/admin issues; redeemed via the accept endpoint. |
| `workspace_invite_secrets` | Isolated invite hash | **NEW (0011)** — invite token hash, service-role-only. |
| `magic_link_tokens` | Magic-link audit trail | **NEW (0009)** — Bunkai-side record of OTP issuances for replay-correlation + rate-limiting (Supabase owns the real OTP). |
| `magic_link_token_secrets` | Isolated magic-link hash | **NEW (0011)** — token/IP hashes, service-role-only. |
| `idempotency_keys` | POST replay protection | **NEW (0009)** — 24h dedupe of POSTs by `(user, endpoint, key)`; caches the prior response. |
| `activity_log` | Audit-light event trail | **NEW (0009)** — workspace-scoped audit events; written only by `service_role`. |
| `feature_flags` | Gradual-rollout gating | **NEW (0009)** — global/workspace flags for Phase-2 rollout. |
| `user_view_state` | Per-user UI persistence | **NEW (0009)** — saved view state per `(user, project, view_kind)`. |

**Key cardinalities** (for test-data planning):
- 1 workspace -> N members, N projects, N invites, N PATs (PATs may be global = `workspace_id` null, or scoped).
- 1 project -> N modules (tree), N ATCs.
- 1 module -> N child modules (max depth 6), N user_stories, N atcs.
- 1 user_story -> N acceptance_criteria, N atcs (the story FK is **RESTRICT** — a story with ATCs cannot be deleted, protecting traceability).
- 1 atc -> N steps, N assertions, >= 1 acceptance_criteria via `atc_acceptance_criteria`.
- 1 access_token -> exactly 1 `access_token_secrets`; 1 invite -> 1 `workspace_invite_secrets`; 1 magic_link_token -> 1 `magic_link_token_secrets`.

**Notable relationship rules**:
- `workspaces.owner_user_id` is **ON DELETE RESTRICT** — a Supabase auth user cannot be deleted while they still own a workspace.
- `atcs.user_story_id` is **ON DELETE RESTRICT** (everything else in the authoring tree cascades). This is the structural guarantee that traceability survives.
- `access_tokens.workspace_id` is **nullable**: NULL = a global/cross-workspace token (admin/AI enumeration); non-null = a token scoped to one tenant.
- The three `*_secrets` tables are 1:1 children isolated specifically so secret hashes are unreadable by anything except `service_role` (see Flow F and §7).

## 3. Business flows

### Flow A — Account bootstrap (a user's first login)

```
[Email] --> POST /api/v1/auth/magic-link        (public; validate email + next)
   |            supabase.auth.signInWithOtp({ emailRedirectTo: /auth/callback?next=.. })
   |            best-effort audit row in magic_link_tokens (+ secret sibling)
   v
[Click link] --> GET /auth/callback?code=..&next=/projects
   |               supabase.auth.exchangeCodeForSession(code)  -> sets session cookie
   |               open-redirect guard: next must be root-relative
   v
302 -> /projects     (Next middleware refreshes session on every navigation)
   |
   |-- no membership? --> /onboarding
   |                         OnboardingForm: POST /api/v1/workspaces { slug, name }
   |                         -> RPC bunkai_bootstrap_workspace (SECURITY DEFINER)
   |                            atomic INSERT workspaces + workspace_members(owner)
   v
302 -> /projects (now populated)
```

- **Tables mutated**: `auth.users` (Supabase), `workspaces`, `workspace_members`, best-effort `magic_link_tokens` + `magic_link_token_secrets`.
- **Business rules**: workspace slug must match `^[a-z0-9][a-z0-9-]{1,38}[a-z0-9]$` and avoid the reserved-slug blocklist; the creator is auto-enrolled as `owner`; the bootstrap is atomic to resolve the chicken-and-egg where `workspace_members` INSERT normally requires already being admin.
- **Code paths**: `app/api/v1/auth/magic-link/route.ts`, `app/auth/callback/route.ts`, `middleware.ts`, `app/(app)/onboarding/`, RPC `bunkai_bootstrap_workspace` (`0006`).

### Flow A' — Headless sign-up / sign-in (CLI + agent onboarding) — NEW

```
POST /api/v1/auth/signup   { email, password, pat_name?, pat_scopes?, pat_expires_in_days? }
   |   admin.createUser(email_confirm:true)  (no email sent)
   |   signInWithPassword  -> session cookies
   |   mintPat (default name "cli-signup", default scopes = all four)
   v
201 { user, session{access_token,refresh_token,..}, pat{ token: bk_pat_.. }, warning }

POST /api/v1/auth/signin   (same body) -> 200 { user, session, pat (name "cli-signin") }
   |   uniform 401 on failure (never leaks email-vs-password)
```

- **Why it exists**: lets a CLI or agent provision an account and obtain BOTH a session and a usable PAT in one round trip — no browser, no magic-link inbox.
- **Tables mutated**: `auth.users`, `access_tokens` + `access_token_secrets`.
- **Code paths**: `app/api/v1/auth/signup/route.ts`, `app/api/v1/auth/signin/route.ts`, shared `lib/api/pat.ts` (`mintPat`).

### Flow B — Authoring (build a Project + Module tree + Story + AC + ATC)

```
/projects (workspace home; project-list/create UI is still a Phase-E stub)
   |  Create Project  --> INSERT projects
   v
/projects/[projectSlug]   (Topbar + module-explorer Sidebar + ATC table)
   |  Add Module (root or child) --> INSERT modules (path depth <= 6)
   |  Add User Story to module    --> INSERT user_stories (optional external_id -> Jira)
   |  Add Acceptance Criterion    --> INSERT acceptance_criteria (unique position per story)
   v
/projects/[projectSlug]/atcs/[atcId]   (ATC editor: Monaco steps + assertions)
   |  Anchor to a Story + >= 1 AC   (UI blocks save until "Moat: ENFORCED")
   |  "Save ATC"  --> Next server action saveAtcAction --> RPC bunkai_save_atc(...)
   v
RPC bunkai_save_atc (SECURITY INVOKER, one transaction):
   UPDATE atcs header + bump version + updated_at
   DELETE+re-INSERT atc_steps, atc_assertions, atc_acceptance_criteria from the payload
```

- **Tables mutated**: `projects`, `modules`, `user_stories`, `acceptance_criteria`, `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`.
- **Triggers fired**: `atcs_set_updated_at`, `atcs_refresh_tsv` (see §6).
- **Business rules**: save is rejected unless the ATC has a Story set AND >= 1 AC AND a non-empty title (enforced both in the editor and re-validated in the server action). The RPC treats steps/assertions/ACs as one replace-on-write block — child row ids are not preserved.
- **Code paths**: `app/(app)/projects/[projectSlug]/atcs/[atcId]/{page.tsx,actions.ts}`, `components/atcs/AtcEditor.tsx`, RPC `bunkai_save_atc` (`0007`). NOTE: ATC save uses a Next **server action**, not a `/api/v1` fetch; server pages read Supabase directly under RLS.

### Flow C — Teammate invitation + acceptance — NEW (replaces the old "manual run" flow C)

```
ADMIN/OWNER, on /workspaces/[id]/members:
   POST /api/v1/workspaces/{id}/invites  { email, role: viewer|member|admin }
      INSERT workspace_invites (7-day expiry)  + token hash in workspace_invite_secrets
      MVP: NO email sent -- accept_url returned once + copied to clipboard + logged to stdout
      |
      |  manage: POST .../{inviteId} = rotate/resend (fresh secret + new expiry)
      |          DELETE .../{inviteId} = revoke (set revoked_at)
      v
INVITEE opens /invites/accept?token=bk_inv_..   (public landing; prompts sign-in if needed)
   POST /api/v1/invites/accept  { token }
      resolve invite by hash (service_role)
      GUARD ORDER:  revoked? -> 409
                    already accepted? -> 409
                    expired? -> 409
                    caller.email != invite.email? -> 403
      upsert workspace_members -> status 'active' with the invite's role (promotes 'invited')
      stamp accepted_at + accepted_by_user_id
      200 { ok, workspace_id, role }
```

- **Tables mutated**: `workspace_invites`, `workspace_invite_secrets`, `workspace_members`.
- **Business rules**: invites can grant `viewer`/`member`/`admin` only — **never `owner`**. The email-match guard prevents a signed-in user redeeming an invite addressed to someone else. Invite status (`pending`/`accepted`/`revoked`/`expired`) is **derived** from timestamp columns, not stored as an enum. Issuing/revoking/rotating is RLS-gated to workspace admins.
- **Code paths**: `app/api/v1/workspaces/[id]/invites/{route.ts,[inviteId]/route.ts}`, `app/api/v1/invites/accept/route.ts`, `app/(app)/workspaces/[id]/members/`, `app/invites/accept/`.

### Flow D — Token introspection + active-workspace selection (dual-mode auth path) — NEW

```
SESSION or PAT caller:
   GET /api/v1/me          (genuinely dual-mode: cookie OR Bearer via requireAuth)
      -> { user, workspaces[], active_workspace_id, auth{ source, scopes } }
      Bearer path uses the admin client + re-implements tenant scoping in JS
      (auth.uid() is unset under service_role, so RLS would return zero rows)
   GET /api/v1/workspaces  (also genuinely dual-mode) -> active memberships

   POST /api/v1/me/active-workspace { workspace_id }   (COOKIE-only in code)
      verify membership under RLS -> set httpOnly bk_active_ws cookie
      (does NOT touch the Supabase JWT)
```

- **Why it exists**: gives an agent a single call to discover its identity, scopes, and visible workspaces; gives a human UI a way to switch the active tenant.
- **Dual-mode rule**: `requireAuth` checks **Bearer first** so a stale cookie cannot shadow an explicit PAT. Only `GET /api/v1/me` and `GET /api/v1/workspaces` actually implement the dual path; the active-workspace POST is cookie-only.
- **Code paths**: `app/api/v1/me/route.ts`, `app/api/v1/me/active-workspace/route.ts`, `app/api/v1/workspaces/route.ts`, `lib/api/auth.ts`, `lib/api/middleware/bearer.ts`.

### Flow E — PAT lifecycle (issue, use, revoke)

```
[Cookie-authed user, "API Tokens"]
   POST /api/v1/tokens { name?, scopes[] (>=1), workspace_id?, expires_in_days? <=365 }
      generate 32-byte secret -> base64url
      store SHA-256(FULL secret) in access_token_secrets.hash   (NEW location)
      store token_prefix(12) + metadata in access_tokens
      201 { token: "bk_pat_<prefix>.<secret>", warning } -- raw secret returned ONCE
   |
   v
[Agent calls /api/v1/* with Authorization: Bearer bk_pat_<prefix>.<secret>]
   requireBearerToken (NOW IMPLEMENTED):
      O(1) prefix-index lookup in access_tokens
      fetch hash from sibling access_token_secrets (admin client)
      compare SHA-256(prefix + remainder) == stored hash
      reject if revoked_at != null OR expires_at < now()
      fire-and-forget UPDATE last_used_at
   |
   v
GET /api/v1/tokens  -> list caller's tokens (no secret)
DELETE /api/v1/tokens/{id}  -> SOFT-revoke (UPDATE revoked_at = now(); never hard-deleted)
```

- **Tables mutated**: `access_tokens`, `access_token_secrets`.
- **Business rules**: a PAT cannot mint another PAT (chicken-and-egg — issuance is cookie-only). Scopes must be a non-empty subset of `{atc:read, atc:write, run:execute, workspace:admin}`. Revocation is an UPDATE, never a DELETE, to preserve the audit trail.
- **Code paths**: `app/api/v1/tokens/{route.ts,[id]/route.ts}`, `lib/api/pat.ts`, `lib/api/middleware/bearer.ts`.

### Flow F — Secret isolation (the 0011/0012 security re-architecture) — NEW, data-shape flow

```
PROBLEM (0011 header): read-only QA roles (qa_inspector_ro / qa_inspector_rw) had
table-level SELECT on access_tokens / magic_link_tokens / workspace_invites, and an
ALTER DEFAULT PRIVILEGES rule auto-granted every new public table to them.
Postgres cannot hide a single column once table SELECT is granted -> they could read
secret hashes.

   BEFORE                                 AFTER (0011 EXPAND -> 0012 CONTRACT)
   +------------------+                   +------------------+   +---------------------+
   | access_tokens    |                   | access_tokens    |   | access_token_secrets|
   |  ... hash <-------+ readable by QA    |  ...(no hash)    |1:1| token_id, hash      |
   +------------------+                   +------------------+   +---------------------+
                                           (QA-readable meta)     RLS on, NO policies,
                                                                  REVOKE from QA/anon,
                                                                  GRANT only service_role
```

- **0011 (EXPAND)**: create the three sibling `*_secrets` tables, backfill existing hashes, drop legacy UNIQUE constraints, make legacy hash columns nullable.
- **0012 (CONTRACT)**: drop `access_tokens.hash`, `magic_link_tokens.token_hash` + `ip_hash`, `workspace_invites.token_hash`.
- **Consequence for tests**: every secret read/write now flows through the admin (`service_role`) client; a QA database role inspecting the main tables sees operational metadata but no credential material.

## 4. State machines

### `atcs.status`

```
unrun --> running --> { pass | fail | blocked | skipped }
   ^----------------------------------------------------'  (re-run)
```

| From | To | Event | Effects |
|---|---|---|---|
| `unrun` | `running` | execution starts | transient state |
| `running` | `pass`/`fail`/`blocked`/`skipped` | execution completes | terminal-ish outcome |
| any outcome | `running` | re-execution | re-enters the loop |

- **Rules**: transitions are free-form (the DB only constrains the value domain, not the order). `bunkai_save_atc` deliberately does **not** touch `status` — only header fields and `version`. **The endpoint/code path that flips status (run execution) was not found in source** -> Discovery Gap.

### `atcs.version`

```
1 --> 2 --> 3 ...   (monotonic; +1 on every bunkai_save_atc)
```

Serves as an optimistic-lock handle so a stale editor can detect a concurrent overwrite.

### `workspace_members.status`

```
invited --> active <--> suspended
            (only 'active' grants any RLS access)
```

| From | To | Event | Effects |
|---|---|---|---|
| (none) | `active` | bootstrap (owner) or invite-accept upsert | full RLS access at the row's role |
| `invited` | `active` | invitee accepts an invite | row promoted in place (onConflict upsert) |
| `active` | `suspended` | admin UPDATE | member locked out (RLS filters `status='active'`) |
| `suspended` | `active` | admin UPDATE | access restored |

### `workspace_invites` lifecycle (derived from timestamp columns) — NEW

```
                 +-----------+
  issue -------->|  pending  |
                 +-----+-----+
        accept (token) | | revoke (admin)         time passes
                       v v                            v
                 +----------+   +---------+      +---------+
                 | accepted |   | revoked |      | expired |
                 +----------+   +---------+      +---------+
```

| From | To | Event | Effects |
|---|---|---|---|
| (none) | `pending` | admin/owner POST invite | row + secret created, 7-day `expires_at` |
| `pending` | `accepted` | invitee POSTs valid token | `workspace_members` upsert to `active`; stamps `accepted_at` + `accepted_by_user_id` |
| `pending` | `revoked` | admin DELETE/revoke | `revoked_at` set; subsequent accept -> 409 |
| `pending` | `expired` | `expires_at < now()` | passive; accept -> 409 |

- **Rules**: accept guard order is revoked (409) -> already-accepted (409) -> expired (409) -> wrong-email (403). Rotate/resend resets `expires_at` and clears revoked/accepted state with a fresh secret.

### `access_tokens` lifecycle

```
active (revoked_at NULL AND (expires_at NULL OR expires_at >= now()))
   |--- revoke (UPDATE revoked_at) --> revoked   [terminal; need a new PAT]
   `--- time passes (expires_at < now()) --> expired
```

| From | To | Event | Effects |
|---|---|---|---|
| (none) | `active` | mint (insert) | usable bearer token |
| `active` | `active` | each successful auth | fire-and-forget `last_used_at` touch |
| `active` | `revoked` | DELETE endpoint | bearer middleware rejects it; row retained for audit |
| `active` | `expired` | clock | bearer middleware rejects it |

### `idempotency_keys.status` — NEW

```
pending --> succeeded | failed     (24h TTL via expires_at; caches response_snapshot)
```

### `magic_link_tokens` (audit) — NEW

```
issued --> consumed | expired      (1h TTL; service_role-only writes; audit-only)
```

## 6. Automatic processes

### DB triggers (all on `atcs`, from `0004`)

| Trigger | Fires on | Action | Why it exists |
|---|---|---|---|
| `atcs_set_updated_at` | BEFORE UPDATE on `atcs` | sets `NEW.updated_at = now()` via `bunkai_set_updated_at()` | keeps `updated_at` fresh without app code |
| `atcs_refresh_tsv` | BEFORE INSERT OR UPDATE OF (title, tags) on `atcs` | rebuilds `NEW.tsv = to_tsvector('english', title + tags)` via `bunkai_atcs_refresh_tsv()` | `to_tsvector` isn't IMMUTABLE enough for a GENERATED column, so a trigger maintains the GIN-indexed search column |

### RPCs / functions

| RPC | Migration | Security | Purpose |
|---|---|---|---|
| `bunkai_is_workspace_member(ws_id)` | `0005` | DEFINER, STABLE | RLS helper — active member check |
| `bunkai_can_write_workspace(ws_id)` | `0005` | DEFINER, STABLE | RLS helper — role in {member,admin,owner} + active |
| `bunkai_is_workspace_admin(ws_id)` | `0005` | DEFINER, STABLE | RLS helper — role in {admin,owner} + active |
| `bunkai_is_workspace_owner(ws_id)` | `0005` | DEFINER, STABLE | RLS helper — role = owner + active |
| `bunkai_bootstrap_workspace(slug, name)` | `0006` | DEFINER | atomic workspace + owner-membership INSERT; validates slug regex + non-empty name |
| `bunkai_save_atc(atc_id, title, layer, tags, us_id, steps jsonb, assertions jsonb, ac_ids uuid[])` | `0007` | INVOKER | single-transaction full-replace ATC save; bumps `version`; never touches `status` |

The four RLS helpers are `SECURITY DEFINER` specifically to break a 42P17 infinite-recursion loop (a policy that EXISTS-subqueries `workspace_members` from inside RLS recurses). Encapsulating the check in a definer function that bypasses RLS internally breaks the loop.

### App-layer auto-side-effects (NOT DB triggers)

| Effect | Trigger | Where |

## 7. External integrations

### Supabase (Auth + Postgres + RLS) — LIVE, the spine

```
Browser/CLI/Agent --> Next.js (/api/v1, middleware) --> Supabase
                                                         |- Auth: magic-link OTP, sessions
                                                         |- Postgres: all app data, RLS
                                                         `- service_role: secret-table access
```

- **Data impact**: every protected route and every server page reads/writes through a Supabase client; cookie callers are RLS-scoped by `auth.uid()`, the admin (`service_role`) client bypasses RLS for secret tables and Bearer-path tenant joins.
- **Dependent flows**: ALL of them.
- **Failure behavior**: missing Supabase env vars throw at app boot (`lib/env.ts`) -> 500 on any route importing `env`; unauthenticated hits on `/projects` or `/onboarding` redirect to `/login`. **Env gotcha**: code reads legacy key names (`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) which `.env.example` does NOT list (it declares the new-style `SUPABASE_PUBLISHABLE_KEY`/`SUPABASE_SECRET_KEY`) — a `.env` filled strictly from the example boots into "Invalid environment variables".

### Scalar API Reference + zod-to-openapi — LIVE (docs)

- The `/api/v1` contract is generated at build time from Zod schemas into `public/openapi.json` and rendered interactively at `/api/docs` (public). If `/api/openapi` fails, the docs page renders empty. No runtime data impact.

### Monaco Editor / TanStack Table — LIVE (UI)

- Monaco backs the ATC step/assertion editors; TanStack Table renders the ATC grid. UI-only.

### Resend (transactional email) — DECLARED, NOT WIRED

- `RESEND_API_KEY` appears in `.env.example` but there is **no Resend SDK import anywhere**. Invite delivery is explicitly MVP-deferred: the accept URL is returned once, copied to the clipboard, and logged to stdout. No user-visible failure — emails simply aren't sent.

### Jira / Atlassian — dev-tooling only (not app runtime)

- `user_stories.external_id`/`external_url` exist to point at an external tracker, but **no bidirectional sync code exists in the app**. The QA framework's own `acli`/sync scripts are tooling, not a runtime integration.

### Declared-but-unwired MCP/agent slots

- `n8n`, `Tavily`, `Supabase MCP control-plane` appear in `.env.example` as agent/MCP tooling. None are app-runtime integrations.

### CI/CD — ABSENT

- No `.github/workflows/`. No automated test/lint gate before deploy (deploy presumed Vercel-auto-via-Git). Matches the project assessment's Medium risk.

## Discovery Gaps

These could not be verified from the migrations, route handlers, or libraries in scope. "Could not verify" is recorded as a gap, never asserted as fact.

1. **Test / Run / run_step_results / Bug entities are still absent** (through migration 0012). The original "manual run" and "agentic run" execution flows cannot be exercised end-to-end. The run-execution code path that would flip `atcs.status` (`unrun` -> `running` -> pass/fail/...) does not exist in source — `bunkai_save_atc` deliberately leaves `status` untouched.
2. **`qa_inspector_ro` / `qa_inspector_rw` roles + the `ALTER DEFAULT PRIVILEGES` auto-grant rule** are referenced only in `0011` comments. No `CREATE ROLE` or grant statement exists in any migration; they are provisioned out-of-band (Supabase dashboard / non-migration script). Same for `service_role` (Supabase-managed).
3. **OpenAPI ↔ implementation auth drift.** The spec advertises `bearerAuth` for 9 operations (`POST /me/active-workspace`, `POST /workspaces`, `GET/PATCH /workspaces/{id}`, all 4 invite ops, `POST /invites/accept`) whose handlers are cookie-only in code. Only `GET /api/v1/me` and `GET /api/v1/workspaces` genuinely implement the dual cookie+Bearer path. Whether this drift is intentional (aspirational spec) or a bug is UNVERIFIED — do not assert Bearer works on those write endpoints.
4. **PAT scope enforcement does not exist at any endpoint.** `requireScope` / `requireScopeOrCookie` are defined but never called anywhere (verified by repo-wide grep). An `atc:read`-only PAT is treated identically to a `workspace:admin` PAT on the two Bearer-capable routes.
5. **Idempotency wiring.** `idempotency_keys` (0009) and `lib/api/idempotency.ts` exist and the `idempotency-key` header is advertised in CORS, but no route handler invokes the middleware (verified). Effectively every POST is treated as a first occurrence.
6. **Magic-link replay/rate-limit enforcement.** `magic_link_tokens` is described as a replay-guard, but the audit row is written best-effort on issuance and **no code reads `consumed_at` to block replays** at callback (callback delegates entirely to Supabase). The rate-limit is whatever Supabase's own 429 provides; a real rate-limit middleware is deferred ("Phase F").
7. **`activity_log`, `feature_flags`, `user_view_state` are schema-ahead-of-feature.** Tables + RLS exist (Wave-0/Wave-6) but no consuming route handler reads or writes them (verified). `feature_flags` therefore is not a working runtime flag system today — gating is schema-only/planned.
8. **`modules.path` materialization logic** (deriving the slash-path from `parent_module_id`) lives in the application layer, not in any DB trigger within these migrations.
9. **Realtime channel naming, Jira sync mechanism, telemetry endpoint, billing entities** — all still unimplemented (unchanged from prior version): no Supabase Realtime channels defined, no Jira sync code, no `/api/v1/telemetry/*`, no `subscriptions`/`invoices`/`stripe_*` tables.
10. **Project list/create UI, command palette, OAuth login** are explicit stubs (Phase D/E); "New ATC"/"New Test" and editor "Cancel" buttons are present but unwired.
11. **Cross-doc staleness to fix elsewhere (not in this file's scope):** the "11 tables / 8 migrations" count is also repeated in `domain-glossary.md` and `SRS/architecture.md`, and `architecture.md` still says the PAT bearer middleware is "Phase F, not implemented." Both are now stale and should be refreshed in their own passes.
