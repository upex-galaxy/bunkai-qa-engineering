# Business Feature Map — Bunkai TMS

> Generated by `/business-feature-map` on 2026-06-01 (CREATE mode). The **feature-centric** complement to `business-data-map.md` (data-centric). Synthesized from the `/api/v1` route handlers + generated OpenAPI spec, the App-Router frontend (`app/`, `components/`), the auth/PAT libraries (`lib/api/*`, `lib/supabase/*`), the migrations `0001`–`0012`, `package.json`, and `.env.example`.
>
> A **feature** here = any capability the system offers (an API endpoint, a UI action, a background process, an integration). Every claim is anchored to source. Anything that could not be verified lives in **§9 Discovery Gaps**, never asserted inline.

- **Core (9)** — the capabilities the product cannot exist without: magic-link auth, headless signup/signin, workspace bootstrap, ATC authoring (the anchoring moat), the module/story/AC tree, PAT lifecycle, Bearer auth, teammate invites, invite acceptance.

## 9. Discovery gaps

MANDATORY. Capabilities that could NOT be verified from code, appear partial, or need team clarification. Mirrors and extends `business-data-map.md` §Discovery Gaps.

1. **Test-run execution is absent.** No `tests`/`runs`/`run_step_results`/`bugs` tables through migration `0012`; the code path that flips `atcs.status` (`unrun`->`running`->pass/fail/...) does not exist. The product can author and anchor ATCs but cannot yet *execute* them. (Entity-blocked — the single largest feature gap.)

2. **OpenAPI ↔ implementation auth drift.** The spec advertises `bearerAuth` for 9 operations (`POST /me/active-workspace`, `POST /workspaces`, `GET/PATCH /workspaces/{id}`, all 4 invite ops, `POST /invites/accept`) whose handlers are **cookie-only** in code. Only `GET /api/v1/me` and `GET /api/v1/workspaces` genuinely implement dual cookie+Bearer. Whether this is aspirational spec or a bug is UNVERIFIED — do not assert Bearer works on the write/invite endpoints.

3. **PAT scope enforcement does not exist at any endpoint.** `requireScope` / `requireScopeOrCookie` are defined but never called (repo-wide grep). An `atc:read`-only PAT behaves identically to a `workspace:admin` PAT. Scope is validated only at mint-time (INV-4), not at use-time.

4. **Authoring-tree write handlers (Project/Module/Story/AC).** The UI surfaces these entities and implies create/edit, but **no wired create/update handler was found** for `projects`, `modules`, `user_stories`, or `acceptance_criteria` (only `atcs` has the `bunkai_save_atc` write path). "New ATC"/"New Test" buttons are unwired stubs. Where these rows actually get created (seed? Studio? a handler not in scope?) is UNVERIFIED.

5. **No token-management UI.** `/api/v1/tokens` (issue/list/revoke) is fully implemented server-side, but no frontend page was found that lets a human manage their PATs. UNVERIFIED whether this is intentional (CLI-only) or a missing UI.

6. **Idempotency, activity_log, feature_flags, user_view_state are schema-ahead-of-feature.** Tables + RLS exist (`0009`); `lib/api/idempotency.ts` is built. But **no route handler invokes** idempotency persistence, and **nothing reads/writes** the other three. `feature_flags` is therefore not a working runtime flag system today.

7. **Magic-link replay / rate-limit enforcement.** `magic_link_tokens` is described as a replay-guard, but the audit row is best-effort on issuance and **no code reads `consumed_at`** to block replays at callback. Rate-limiting is only whatever Supabase's 429 provides ("Phase F" for real middleware).

8. **`qa_inspector_ro` / `qa_inspector_rw` roles.** Referenced only in `0011` comments; no `CREATE ROLE`/grant in any migration — provisioned out-of-band. The secret-isolation feature (FEAT-018) is *designed* against these roles but their existence is UNVERIFIED in source.

9. **`/workspaces/**` route protection.** The members page is NOT in middleware `PROTECTED_PREFIXES` (only `/projects`, `/onboarding`); gating relies on the in-page `getUser()` check + RLS. UNVERIFIED whether a non-member is reliably blocked at all layers.

10. **ATC acronym definition conflict.** The login UI expands ATC = "Acceptance Test Case"; project doctrine (CLAUDE.md) uses "Acceptance Test Case". Treat as synonyms; needs glossary reconciliation before user-facing test copy.

11. **Realtime, Jira sync, telemetry, billing.** No Supabase Realtime channels, no bidirectional Jira sync code, no telemetry endpoint, no billing/subscription entities — all unimplemented (unchanged from the data map).
