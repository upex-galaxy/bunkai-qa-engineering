## Product

**Bunkai** (分解 — Japanese for "breakdown" / "analysis", a kata-decomposition term) is an **open-core Test Management System** built on Next.js 15 + Supabase. Tagline (working): *"The art of breaking down a kata into its applications."*

Source: `<target>/.context/business/business-model.md` L1-L4.

---

## Problem (what hurts that Bunkai fixes)

Existing TMSs (Xray, Zephyr Scale, TestRail, qTest) are "document vaults with execution glued on top". They store test cases but do not enforce engineering discipline.

> "Test cases written without structure. Pasos sueltos, validations unclear, no link to user story or acceptance criterion. […] Mantenimiento imposible […] Trazabilidad rota […] Reports lie […] Bug management is delegated to Jira."

Found in: `<target>/.context/business/business-model.md` L9-L21.

The deeper pain: incumbent TMSs are *pedagogically neutral* — they let bad QA happen efficiently. They never push the team toward good practice.

Source: `<target>/.context/PRD/executive-summary.md` L22-L24:

> "Bunkai is a TMS whose **data model enforces structure** so good QA is the path of least resistance, not an upsell."

A second commercial driver: regulated industries (fintech / healthtech / legaltech) cannot legally store specs and test data on third-party SaaS — they either pay enterprise licensing or build internal hacks.

Source: `<target>/.context/PRD/executive-summary.md` L10-L20.

---

## Solution philosophy

Bunkai attacks the problem from the **data model**, not the feature list.

> "An ATC without a user story cannot exist. A test without ATCs cannot exist. A bug without a module cannot exist. The structure of the product teaches good QA simply by how it works."

Found in: `<target>/.context/business/business-model.md` L19-L21.

This is enforced at the database level — the `atcs.user_story_id` column is `NOT NULL REFERENCES public.user_stories(id) ON DELETE RESTRICT` (target migration `0004_atcs.sql`), and the M:N table `atc_acceptance_criteria` makes the AC anchor non-optional in practice (the application layer requires ≥1 row per ATC).

## Value propositions

| # | Value prop | DB / code evidence |
|---|---|---|
| 1 | **One-edit-many-tests maintenance** — edit ATC-001 once, every test chaining it updates. | `atcs.version` integer column + `bunkai_save_atc` RPC increments on every save (`0004_atcs.sql`, `0007_save_atc.sql`). |
| 2 | **Structural traceability enforced, not optional** — every ATC anchors to US + ≥1 AC. | NOT NULL constraint on `atcs.user_story_id`; M:N table `atc_acceptance_criteria` (`0004_atcs.sql`). |
| 3 | **Three execution modes share one data model** — manual, agentic (AI), automated (CI/CD) — comparable runs against the same ATCs. | `atcs.status` enum + `access_tokens.scopes` including `run:execute` (`0004_atcs.sql`, `0008_access_tokens.sql`). |
| 4 | **Native defect management** anchored to module + ATC + run. Optional Jira sync — not delegation. | (Bug entity is documented in source business-model L45-L52; database schema for bugs not yet migrated as of `0008_access_tokens.sql` — see Discovery Gaps.) |
| 5 | **API-first for AI operators** — REST + OpenAPI + CLI. | 6 | **Open-core / self-hostable** — data sovereignty by ownership, not contract. | `workspaces.plan` enum: `community` / `cloud` / `enterprise` (`0001_tenancy.sql` L32-L33). |

## Access model (RBAC + PAT scopes)

| Layer | Mechanism | Values |
|---|---|---|
| Workspace membership | `workspace_members.role` enum | `viewer` · `member` · `admin` · `owner` |
| Workspace membership | `workspace_members.status` enum | `active` · `invited` · `suspended` |
| API tokens | `access_tokens.scopes` array (must be non-empty subset) | `atc:read` · `atc:write` · `run:execute` · `workspace:admin` |
| API tokens | `access_tokens.workspace_id` | NULL = global / cross-workspace token (admin or AI-agent use cases); non-NULL = per-workspace scope |

Source: `0001_tenancy.sql` L40-L48 + `0008_access_tokens.sql` L1-L14, L28-L36.

For the QA framework's authentication strategy:
- E2E tests → magic-link Supabase Auth (UI), authenticated session cookie.
- API tests → PAT with appropriate scope; e.g., a read-only smoke probe uses a PAT with only `atc:read`.

## MVP success metrics (KPIs)

From `<target>/.context/PRD/executive-summary.md` L37-L47:

| Category | Metric | Target |
|---|---|---|
| Adoption | Workspaces completing activation (≥1 Module + ≥1 ATC + ≥1 Test + ≥1 Run in first 24h) | ≥60% |
| Engagement | Avg ATCs created per active workspace in week 1 | >10 |
| Engagement | Tests-per-ATC ratio (reuse) at day 30 | <1.0 (each ATC reused in >1 test) |
| Retention | Week-4 retention of new workspaces | >40% |
| Structural correctness | % of ATCs anchored to a US + AC (data-model guarantee) | 100% |
| Distribution signal | GitHub stars within 60 days | >500 |
| Distribution signal | Docker Compose installs reported via opt-in telemetry | >20 |

These are useful for the QA framework's regression strategy: any test that breaks `atc.user_story_id NOT NULL` or `atc_acceptance_criteria` constraints is a P0 — it would silently violate the "100% anchoring" KPI.
