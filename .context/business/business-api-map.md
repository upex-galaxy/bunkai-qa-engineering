## 1. Executive summary

Bunkai TMS lets two very different populations operate the same multi-tenant test-management product through one REST surface. A **human QA engineer** signs in passwordlessly, lands in a workspace, invites teammates, and authors test cases that the database refuses to save unless they are anchored to a User Story and at least one Acceptance Criterion. A **machine** — a CLI or an AI agent — provisions itself, mints a scoped bearer token, and reads or writes the same test assets without ever touching a browser. The API's job is to make both of those callers first-class while keeping each tenant's data and every credential hash strictly isolated.

From the business' point of view the API enables four things end to end: **get in** (passwordless magic-link for humans, headless signup/signin that returns a usable token for machines), **set up a tenant** (create a workspace and become its owner in one atomic call, then invite teammates by email), **author the core asset** (build a Project → Module → Story → Acceptance-Criterion tree and write richly-structured ATCs that cannot escape the anchoring rule), and **hand off to automation** (issue, list, and revoke Personal Access Tokens so a scoped agent can consume the data over a documented contract). Authorization is enforced primarily by Postgres Row-Level Security keyed to workspace membership and role — the API handlers mostly trust the database to be the boundary, with a thin layer of application-level re-checks for defence in depth.

The newest engineering theme visible at the API boundary is **secret hygiene**: token, invite, and magic-link secret hashes were moved out of their main tables into service-role-only sibling tables, so the only code that can read a credential hash is the privileged admin client — never a cookie-scoped session and never a read-only QA database role. Two honest caveats shape every test plan against this API: bearer-token auth is genuinely wired on only two of the eleven endpoints the spec advertises for it (the other nine are cookie-only), and PAT scopes are checked when a token is minted but never enforced when it is used. Both are documented as Discovery Gaps, not asserted as working behavior.

## 2. Permission & auth model

Bunkai has **four authentication tiers**, not a single "protected" bucket. Two of them establish a session, the third *is* that session as carried by a cookie, and the fourth is an independent bearer credential for machines. Higher privilege is never granted by the auth tier itself — it is granted by **workspace role** (`viewer < member < admin < owner`) evaluated inside Postgres RLS.

| Tier | Who it applies to | How to acquire | Where enforced (code path) |
|---|---|---|---|
| **A — Magic-link OTP** | Humans, passwordless | `POST /api/v1/auth/magic-link` emails a link → `GET /auth/callback` exchanges the code | Issuance + verification delegated to **Supabase Auth** (`signInWithOtp`, `exchangeCodeForSession` in `app/auth/callback/route.ts`); Bunkai's own `magic_link_tokens` rows are audit-only |
| **B — Password signin/signup** | CLI tools, AI agents | `POST /api/v1/auth/signin` (existing) or `POST /api/v1/auth/signup` (provisions, `email_confirm:true`) | Route handler delegates to Supabase `signInWithPassword`; uniform `401` on failure (no email-existence leak). Both calls **also mint a PAT** in the same round trip |
| **C — Session cookie** | Browser + cookie-bearing callers | Set by Tier A callback or Tier B password flow (`sb-<ref>-auth-token`) | `supabase.auth.getUser()` on a cookie-built server client (`lib/supabase/server.ts`); Next `middleware.ts` refreshes the session on page navigations; **Postgres RLS** is the actual authorization boundary |
| **D — Personal Access Token (PAT)** | Agents / CLI / CI | `POST /api/v1/tokens` (cookie-authed), or bundled by signin/signup. Format `bk_pat_<prefix>.<secret>` | `requireBearerToken` (`lib/api/middleware/bearer.ts`): prefix-indexed lookup → SHA-256 compare against the service-role-only `access_token_secrets` table → reject if revoked/expired |

A critical nuance for testers: a cookie session under RLS carries **no scopes** (`scopes: []`) — it is unscoped and bounded only by RLS — whereas a PAT carries an explicit scope set drawn from `{atc:read, atc:write, run:execute, workspace:admin}` and an optional workspace binding. When both a cookie and a bearer header are present, `requireAuth` checks **Bearer first** so a stale cookie cannot shadow an explicit token (`lib/api/auth.ts`). Note that Next `middleware.ts` only guards page prefixes (`/projects`, `/onboarding`) — it does **not** gate `/api/*`; every API route does its own per-handler `getUser()` or `requireAuth` check.

## 3. Critical business journeys

Six journeys are documented (cap is 7; six were selected because the seventh candidate — test-*run execution* — does not exist in source and is recorded as a Discovery Gap rather than a traced journey). They are ordered by security/business weight: get-in, provision-tenant, grow-the-team, author-the-asset, mint/revoke-the-machine-credential, and the cross-cutting secret-isolation posture that protects all of them. Note for cross-reference: data-map **Flow D** (dual-mode introspection — `GET /me`, `GET /workspaces`, `POST /me/active-workspace`) has no standalone journey here; its endpoints are covered inside Journey 5 (machine-credential lifecycle), so no flow is orphaned.

### Journey 1 — Human first login (passwordless bootstrap)

**Purpose**: a brand-new human gets from an email address to a populated workspace without a password.

```
  Client            Middleware/Handler        Supabase Auth        Postgres (RPC + RLS)
    |  POST /auth/magic-link  |                    |                       |
    |------------------------>| signInWithOtp ----->| email sent            |
    |  [click link]           |                    |                       |
    |  GET /auth/callback     | exchangeCode ------>| session cookie set    |
    |------------------------>|                    |                       |
    |  302 /projects          |                    |                       |
    |  (no membership)        |                    |                       |
    |  302 /onboarding        |                    |                       |
    |  POST /workspaces       | bunkai_bootstrap_workspace (SECURITY DEFINER)|
    |  {slug,name}            |----------------------------------> INSERT workspaces
    |                         |                    |              + workspace_members(owner) [atomic]
    |  201 {workspace}        |                    |                       |
    |  302 /projects (ready)  |                    |                       |
```

1. Caller requests an OTP email — Bunkai validates the email and the `next` redirect target (must be root-relative; open-redirect guard, INV-9), then hands issuance to Supabase. *Why*: Bunkai never owns the credential; it only orchestrates.
2. The clicked code is exchanged for a session cookie at the callback. *Why*: this is the single moment a human identity becomes a usable session.
3. A user with no active membership is routed to onboarding, which creates a workspace via the atomic bootstrap RPC that also self-enrolls the creator as `owner`. *Why*: a plain INSERT would deadlock the chicken-and-egg where adding a member requires already being an admin.

- **Endpoints involved**: `POST /api/v1/auth/magic-link`, `GET /auth/callback`, `POST /api/v1/workspaces`
- **Entities touched**: `auth.users`, `workspaces`, `workspace_members`, best-effort `magic_link_tokens` (data-map §2) — Flow A.
- **Feature IDs**: FEAT-001 (magic-link), FEAT-003 (workspace bootstrap)

### Journey 2 — Headless agent onboarding (one call → session + token)

**Purpose**: a CLI or AI agent provisions an account and walks away with a usable bearer token, no browser, no inbox.

```
  Agent             Handler                  Supabase Admin/Auth      Postgres
    |  POST /auth/signup {email,password,pat_*}    |                    |
    |--------------------------------------------->| admin.createUser   |
    |                  |                            |  (email_confirm)   |
    |                  | signInWithPassword ------->| session cookies    |
    |                  | mintPat(default all scopes)--------------> INSERT access_tokens
    |                  |                            |              + access_token_secrets
    |  201 {user, session, pat:{token}}            |                    |
    |<---------------------------------------------|  secret returned ONCE
```

1. `signup` provisions the user with `email_confirm:true` so no email round-trip is needed; `signin` does the same for an existing user. *Why*: agents cannot click a magic link.
2. The handler signs the user in (session cookies) and immediately mints a PAT (default name `cli-signup`/`cli-signin`, default scopes = all four). *Why*: one round trip yields everything an automation needs — a session for cookie-only endpoints and a token for bearer endpoints.
3. The raw `bk_pat_…` is returned exactly once; only its SHA-256 hash persists. *Why*: token-replay protection (INV-10).

- **Endpoints involved**: `POST /api/v1/auth/signup`, `POST /api/v1/auth/signin`
- **Entities touched**: `auth.users`, `access_tokens`, `access_token_secrets` (data-map §2) — Flow A'.
- **Feature IDs**: FEAT-002 (headless auth)

### Journey 3 — Grow the team (invite → accept)

**Purpose**: an owner/admin brings a teammate into the tenant at a chosen role, and the teammate joins by redeeming a token.

```
  Admin             Invite Handler           Postgres (RLS admin-gated)     Invitee
    |  POST /workspaces/{id}/invites {email,role}   |                          |
    |---------------------------------------------->| INSERT workspace_invites |
    |                  |  (token hash -> workspace_invite_secrets, service_role)|
    |  201 {invite, token, accept_url}              |  [MVP: no email; URL logged + clipboard]
    |<----------------------------------------------|                          |
    |                  |                            |                          |
    |   ............... accept_url shared out-of-band .......................> |
    |                                               |   POST /invites/accept {token}
    |                                               |<-------------------------|
    |                  | resolve invite by hash (service_role)                 |
    |                  | GUARD: revoked?409 -> accepted?409 -> expired?409 ->   |
    |                  |        caller.email != invite.email?403               |
    |                  | upsert workspace_members status='active' (role)       |
    |                  | stamp accepted_at + accepted_by_user_id               |
    |                  |  200 {ok, workspace_id, role} ----------------------->|
```

1. An admin/owner issues an invite by email + role; RLS gates issuance to admins. *Why*: only admins may expand the tenant.
2. Because transactional email is not wired (MVP), the accept URL is returned once, copied to the clipboard, and logged to stdout. *Why*: the link must reach the invitee somehow until Resend is wired (see §5).
3. The invitee redeems the raw token; the handler runs a strict guard order (revoked → already-accepted → expired → email-mismatch) before upserting membership to `active`. *Why*: the role can never be `owner` and the redeemer's email must match the invite — both prevent privilege escalation / invite hijack (INV-12).

- **Endpoints involved**: `POST`/`GET /api/v1/workspaces/{id}/invites`, `POST`/`DELETE /api/v1/workspaces/{id}/invites/{inviteId}`, `POST /api/v1/invites/accept`
- **Entities touched**: `workspace_invites`, `workspace_invite_secrets`, `workspace_members` (data-map §2) — Flow C.
- **Feature IDs**: FEAT-006 (invitation), FEAT-007 (acceptance), FEAT-008 (members view)

### Journey 4 — Author the core asset (ATC with the anchoring moat)

**Purpose**: a member builds the product's reason to exist — a test case that physically cannot be saved untraced.

```
  Member (browser)        Next Server Action        Postgres (RPC, INVOKER under RLS)
    |  build Project/Module/Story/AC tree (server-page Supabase writes under RLS)
    |  open ATC editor: title, layer, steps(md), assertions(yaml), tags
    |  anchor to 1 Story + >=1 AC   [UI: "Moat: ENFORCED" gates Save]
    |  Save ATC (Cmd+S)              |                          |
    |------------------------------->| saveAtcAction            |
    |                                | re-validate: story + >=1 AC + non-empty title
    |                                | bunkai_save_atc(...) ----> UPDATE atcs + bump version
    |                                |                            DELETE+re-INSERT
    |                                |                              atc_steps / atc_assertions /
    |                                |                              atc_acceptance_criteria
    |  redirect / toast              |                          |  (triggers: set_updated_at, refresh_tsv)
    |<-------------------------------|                          |
```

1. Member assembles the tree (Project → Module → Story → Acceptance Criterion) and opens the ATC editor. *Why*: an ATC must point at a Story and the criteria it verifies.
2. The UI blocks Save until the moat is satisfied; the server action **re-validates** story + ≥1 AC + non-empty title before calling the RPC. *Why*: client validation alone is not a security boundary — INV-1/INV-2 are re-checked server-side.
3. `bunkai_save_atc` runs a single-transaction full-replace of steps/assertions/AC-links and bumps `version` (optimistic lock). *Why*: child rows are treated as a replace-on-write block, so a stale editor can detect a concurrent overwrite.

Note: ATC save uses a **Next server action**, not a `/api/v1` fetch — so this journey is not in the OpenAPI spec; it is RPC-contract-tested, not endpoint-tested.

- **Endpoints involved**: none under `/api/v1` (server action `saveAtcAction` → RPC `bunkai_save_atc`)
- **Entities touched**: `projects`, `modules`, `user_stories`, `acceptance_criteria`, `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria` (data-map §2) — Flow B.
- **Feature IDs**: FEAT-010 (ATC authoring/moat), FEAT-011 (tree), FEAT-012 (ATC grid)

### Journey 5 — Machine credential lifecycle (issue → use → revoke)

**Purpose**: a human hands an agent a scoped, revocable credential and can shut it off without deleting history.

```
  User (cookie)      Tokens Handler           Postgres
    |  POST /tokens {scopes[],workspace_id?,expires_in_days?}|
    |------------------------------------------>| generate 32B secret -> base64url
    |                  | store SHA-256(FULL) ----> access_token_secrets (service_role)
    |                  | store prefix(12)+meta --> access_tokens
    |  201 {token:"bk_pat_<p>.<s>"}             |  raw secret ONCE
    |<------------------------------------------|
    |                  |                         |
  Agent (bearer)       |                         |
    |  GET /api/v1/me  (Authorization: Bearer ..)|  requireBearerToken: hash compare
    |  GET /tokens     -> list (no secret)       |  RLS: auth.uid()=user_id
    |  DELETE /tokens/{id}  -> SOFT-revoke ------>| UPDATE revoked_at=now() (never DELETE)
    |                  |  bearer middleware now rejects that token (revoked)
```

1. A cookie-authed user mints a PAT with ≥1 scope, an optional workspace binding, and optional expiry (≤365 days). *Why*: a PAT cannot mint a PAT (issuance is cookie-only) — that breaks a credential-escalation loop.
2. The agent authenticates each call with the bearer token; the middleware reconstructs the **full** secret (`prefix + remainder`) before hashing (INV-13 — a previously-fixed bug where hashing only the remainder caused permanent 401s). *Why*: the stored hash is of the full secret.
3. Revocation is a soft `UPDATE revoked_at` (INV-14); the bearer middleware then rejects the row. *Why*: hard-deleting would destroy the audit trail.

- **Endpoints involved**: `POST`/`GET /api/v1/tokens`, `DELETE /api/v1/tokens/{id}`, plus bearer verification on `GET /api/v1/me` / `GET /api/v1/workspaces`
- **Entities touched**: `access_tokens`, `access_token_secrets` (data-map §2) — Flow E.
- **Feature IDs**: FEAT-013 (PAT lifecycle), FEAT-014 (Bearer auth)

### Journey 6 — Secret isolation (the posture that guards every other journey)

**Purpose**: not a user click-path but a data-shape guarantee — credential hashes are unreadable by anything except the privileged admin client, so read-only QA/analytics database roles never see them.

```
  BEFORE (0011)                          AFTER (0011 EXPAND -> 0012 CONTRACT)
  +-----------------+                    +-----------------+   +---------------------+
  | access_tokens   | hash readable      | access_tokens   |1:1| access_token_secrets|
  |  ... hash <-----+ by QA roles        |  ...(no hash)   |---| token_id, hash      |
  +-----------------+                    +-----------------+   +---------------------+
                                          QA-readable meta      RLS on, NO policies,
                                                                REVOKE from QA/anon,
                                                                GRANT only service_role

  Every secret read/write path now goes through the admin (service_role) client:
    bearer verify, PAT mint, invite issue/rotate/accept, magic-link audit insert.
```

1. The problem (0011 header): read-only QA roles held table-level SELECT on the secret-bearing tables, and Postgres cannot hide a single column once table SELECT is granted. *Why it mattered*: a QA/analytics role could read credential hashes.
2. **EXPAND (0011)**: three 1:1 `*_secrets` sibling tables created, hashes backfilled, RLS enabled with *no* policies, all access REVOKEd from QA/anon and GRANTed only to `service_role`.
3. **CONTRACT (0012)**: the legacy hash columns dropped from the main tables. *Consequence*: a QA database role inspecting `access_tokens` / `workspace_invites` / `magic_link_tokens` sees operational metadata but no credential material (INV-11).

- **Endpoints involved**: none directly — transparent to all secret read/write paths (bearer verify, PAT mint, invite issue/accept, magic-link audit)
- **Entities touched**: `access_token_secrets`, `workspace_invite_secrets`, `magic_link_token_secrets` (data-map §2) — Flow F.
- **Feature IDs**: FEAT-018 (secret isolation)

## 4. Architecture behind the API

Bunkai is a single Next.js 15 (App Router) application deployed on Vercel; there is no separate backend service. "Handlers" are Route Handlers under `app/api/v1/`, plus a handful of Next **server actions** (the ATC save path) and **server components** that read Supabase directly under RLS. All persistence and all authorization live in one Supabase Postgres instance. The only external moving part in the request path is Supabase Auth.

```
  CLIENT                  EDGE / APP                  HANDLERS / ACTIONS         PERSISTENCE / EXTERNAL
  +----------+   +------------------------+   +---------------------------+   +-----------------------+
  | Browser  |   | Next middleware        |   | Route Handlers /api/v1/*  |   | Supabase Postgres     |
  | CLI      |-->|  (session refresh,     |-->|  withApiHandler wrapper   |-->|  RLS (auth.uid()+role)|
  | AI agent |   |   page-prefix guard    |   |  getUser() / requireAuth  |   |  RPCs (DEFINER/INVOKER)|
  +----------+   |   ONLY /projects,      |   +------------+--------------+   +-----------+-----------+
                 |   /onboarding)         |                |                              |
                 +------------------------+   +------------v--------------+   +-----------v-----------+
                                              | Server actions (ATC save) |   | service_role admin    |
                                              | Server components (reads) |-->|  client (bypass RLS:  |
                                              +------------+--------------+   |  *_secrets, Bearer    |
                                                           |                  |  tenant joins)        |
                                                           |                  +-----------+-----------+
                                                           |                              |
                                                           v                  +-----------v-----------+
                                              +---------------------------+   | Supabase Auth         |
                                              | cookie server client      |-->|  magic-link OTP,      |
                                              |  (RLS-scoped by auth.uid())|   |  sessions, password   |
                                              +---------------------------+   +-----------------------+
```

| Component | Role | Persistence / integrations touched | Why it matters for QA |
|---|---|---|---|
| Next middleware | Refreshes session, redirects unauthenticated humans away from page prefixes | Supabase Auth (`getUser`) | Does **not** protect `/api/*` — API auth is per-handler. A test asserting "middleware blocks the API" would be wrong. |
| Route Handlers (`/api/v1/*`) | The REST surface (auth, identity, tokens, workspaces, invites) | Cookie client (RLS) or admin client (service_role) | The primary contract-test target; auth tier differs per route (cookie-only vs genuine dual). |
| Server actions (ATC save) | Mutating the core asset off the REST path | RPC `bunkai_save_atc` | The highest-value RPC-contract test; not in OpenAPI, so endpoint tests miss it. |
| Server components | Read the tree/grid directly under RLS | Cookie server client | Reads are RLS-bound; a cross-tenant leak here is an INV-3 failure. |
| Cookie server client | Identity + RLS-scoped data access for humans | Supabase Postgres (RLS) | If RLS is the only boundary, RLS bugs are security bugs. |
| Admin (service_role) client | Reads/writes secrets; re-implements tenant scoping for Bearer | `*_secrets` tables, `workspace_members` joins | Bypasses RLS by design — JS-side scoping is the only tenant guard on Bearer paths. |
| Supabase Auth | OTP issuance, session mint/refresh, password verification | external (Supabase platform) | If Auth hangs, every login/refresh stalls; Bunkai surfaces Supabase's own 429/5xx. |
| RPCs (`bunkai_*`) | Atomic bootstrap, RLS helpers, ATC save | Postgres | DEFINER helpers break an RLS recursion loop; bootstrap is atomic — both are contract-test anchors. |

## 5. External integrations

Only **one** third-party service sits in the live request path: Supabase (Auth + Postgres). Everything else at the boundary is either build-time, declared-but-unwired, or dev-tooling. The failure-mode column is what `business-feature-map.md` §6 omits.

| Service | Trigger | Direction | Failure mode (user-visible) | Journeys affected |
|---|---|---|---|---|
| Supabase Auth | `POST /auth/magic-link`, `POST /auth/signin\|signup`, `GET /auth/callback` | Outbound sync | Supabase 429 → `rate_limited`; other upstream error → `upstream_error`; bad/expired code → redirect `/login?error=otp_exchange_failed` | 1, 2 |
| Supabase Postgres (RLS) | Every protected route + server page | Outbound sync | Missing Supabase env vars → app throws at boot (`lib/env.ts`) → `500` on any route importing `env`; unauth page hit → `302 /login` | all |
| Supabase Admin (service_role) | PAT mint, invite secret write, magic-link audit, Bearer tenant joins | Outbound sync | Missing `SUPABASE_SERVICE_ROLE_KEY` → boot throw → `500`; otherwise transparent | 2, 3, 5, 6 |
| Supabase Auth callback | `GET /auth/callback?code=…` | **Inbound** (the only inbound webhook today) | Invalid/expired code → `/login?error=…`; open-redirect guard rejects non-root-relative `next` | 1 |
| Scalar API Reference + zod-to-openapi | `/api/docs` renders `/api/openapi`; spec built at `bun run openapi:gen` (build-time) | Outbound sync (docs) | If `/api/openapi` 500s, the docs page renders empty; no runtime data impact | (docs only) |
| Resend (transactional email) | Intended for invite delivery | Outbound sync | **DECLARED, NOT WIRED** — `RESEND_API_KEY` in `.env.example`, no SDK import. No user-visible failure: the invite email is simply never sent; the accept URL is logged + clipboarded instead | 3 (degraded) |
| Jira / Atlassian | `user_stories.external_id`/`external_url` (data reference) | none at runtime | No bidirectional sync code in the app; the QA framework's `acli`/sync scripts are tooling, not a runtime path | (data ref only) |
| Tavily / n8n / Supabase MCP | Agent/MCP slots in `.env.example` | none at runtime | Declared agent tooling, not app-runtime integrations | none |
| CI/CD (GitHub Actions) | — | — | **ABSENT** — no `.github/workflows/`; no automated test/lint gate before deploy (Vercel-auto-via-Git presumed) | none |

## 7. Discovery gaps

MANDATORY. Anything that could not be verified from the route handlers, libraries, middleware, or migrations in scope. Mirrors and extends the Discovery Gaps in `business-data-map.md` §Discovery Gaps and `business-feature-map.md` §9.

1. **Journey cap decision.** The seventh candidate critical journey — **test-run execution** (the path that would flip `atcs.status` from `unrun` → `running` → pass/fail) — **does not exist in source** through migration `0012`. No `tests`/`runs`/`run_step_results`/`bugs` tables, and `bunkai_save_atc` deliberately never touches `status`. Six journeys are documented rather than seven; the missing one is entity-blocked, not omitted.

2. **OpenAPI ↔ implementation auth drift (do not assert Bearer works).** The spec advertises `bearerAuth` for **11 operations total**: **9 of them** (`POST /me/active-workspace`, `POST /workspaces`, `GET`/`PATCH /workspaces/{id}`, all 4 invite ops, `POST /invites/accept`) have handlers that are **cookie-only** in code (they call `supabase.auth.getUser()`, never `requireAuth`), while only the remaining **2** — `GET /api/v1/me` and `GET /api/v1/workspaces` — genuinely implement the dual cookie+Bearer path. A Bearer-only caller hitting any of those 9 cookie-only operations gets `401`, contradicting the documented contract. Whether the drift is aspirational spec or a bug is **UNVERIFIED**.

3. **PAT scope enforcement does not exist at any endpoint.** `requireScope` / `requireScopeOrCookie` are *defined* (`lib/api/middleware/bearer.ts`, `lib/api/auth.ts`) but never *called* anywhere (verified by repo-wide grep). An `atc:read`-only PAT is treated identically to a `workspace:admin` PAT on the two Bearer-capable routes. Scope is validated only at mint-time (INV-4), never at use-time. Do not assume a narrow scope restricts a token's reach.

4. **`/api/*` is not gated by Next middleware.** `middleware.ts` protects only page prefixes (`/projects`, `/onboarding`); API authorization is entirely per-handler. The `/workspaces/{id}/members` page is likewise not in the protected prefixes and relies on an in-page `getUser()` + RLS — whether a non-member is reliably blocked at every layer is **UNVERIFIED**.

5. **Magic-link audit table is not a replay guard in code.** `magic_link_tokens` is *described* as a replay-correlation / rate-limit aid, but the audit row is written best-effort on issuance and **no code reads `consumed_at`** to block replays at callback (the callback delegates entirely to Supabase). The only rate-limit is whatever Supabase's own 429 provides; a real rate-limit middleware is deferred ("Phase F"). Replay/rate-limit enforcement at the API boundary is **UNVERIFIED**.

6. **Idempotency is built but unwired.** `lib/api/idempotency.ts` is implemented and the `idempotency-key` header is advertised in the `OPTIONS /api/v1` CORS response, but **no route handler invokes** the idempotency persistence (verified). Every POST is effectively treated as a first occurrence; the `idempotency_keys` table (`0009`) is schema-ahead-of-feature.

7. **Out-of-band roles.** `qa_inspector_ro` / `qa_inspector_rw` (the roles the §3 Journey 6 secret-isolation posture is designed against) and `service_role` are referenced only in `0011` comments / Supabase platform docs — no `CREATE ROLE` or grant statement exists in any migration. They are provisioned out-of-band, so the secret-isolation feature cannot be fully exercised from migration source alone.

8. **Authoring-tree write handlers (Project/Module/Story/AC).** Journey 4 narrates building the tree, but **no wired create/update handler was found** for `projects`, `modules`, `user_stories`, or `acceptance_criteria` (only `atcs` has the `bunkai_save_atc` write path). "New ATC"/"New Test"/editor "Cancel" buttons are unwired stubs. Where these rows actually get created (seed? Supabase Studio? a handler out of scope?) is **UNVERIFIED**.

9. **No signout/logout route.** No in-app signout endpoint exists; session revocation is Supabase-side. A logout journey could not be traced.

10. **Single-app scope (no monorepo shards unexamined).** The target is one Next.js app; there is no separate backend service or additional shard that this map omits. No webhooks are configured in external dashboards that are discoverable from code beyond the Supabase auth callback.
