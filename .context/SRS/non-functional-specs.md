## 2. Security

### 2.1 Authentication

- **Magic-link only** for human users (no password, no SSO in MVP). SSO/SAML is Enterprise-tier post-MVP.
- **PATs** for headless consumers. 256-bit entropy secrets, SHA-256 at rest, prefix-indexed for O(1) lookup.

### 2.2 Authorization

- **RLS-everywhere**: 11 tables, all with `select/insert/update/delete` policies (with `access_tokens` deliberately omitting `delete` — soft-revoke only — see BR-022).
- **SECURITY DEFINER helpers** (`bunkai_is_workspace_member`, `bunkai_can_write_workspace`, `bunkai_is_workspace_admin`, `bunkai_is_workspace_owner`) avoid 42P17 recursion + centralize role checks.

### 2.3 Secret management

- `SUPABASE_SERVICE_ROLE_KEY` validated by `lib/env.ts` (Zod). Module is `server-only` — TS error if imported in a client bundle.
- Browser client (`lib/supabase/client.ts`) reads only `NEXT_PUBLIC_*` via static `process.env` access so Next.js inlines them at build (not run-time leak vector).
- PATs use `bk_pat_` family prefix → GitHub + GitGuardian secret scanners flag leaks automatically.

### 2.4 Common-vector mitigations

| Vector | Mitigation | Verification (QA framework) |
|---|---|---|
| XSS | React escaping by default; no `dangerouslySetInnerHTML` audited yet | Lint rule + manual review |
| CSRF | Supabase SSR cookie SameSite=Lax by default; magic-link callback is GET (idempotent code exchange) | Smoke: forged Origin → expected behavior |
| Open redirect | `next` validated root-relative in both POST + callback (BR-023) | Negative test: `next=//evil.com` → fallback `/projects` |
| SQL injection | Supabase client + Zod schemas — no raw SQL from user input | n/a (vendor mechanism) |
| Cross-tenant leak | RLS on every table | Smoke: user A reads user B's workspace → 403/404 |
| Token replay | Idempotency-key infra present in code (`lib/api/idempotency.ts`); replay store **not implemented** | **Gap** — cannot test until Phase F |
| Brute-force PAT | 256-bit entropy + SHA-256 + prefix-indexed lookup; **rate-limit not implemented** | **Gap** — cannot test until rate-limit ships |
| Email enumeration | Magic-link returns same response shape regardless of address existence (Supabase default) | Smoke: known + unknown email → same status + similar timing |
| Service-role-key leak | `server-only` import-time check | Build artifact grep: no `SUPABASE_SERVICE_ROLE_KEY` literal in `.next/static/**` |

### 2.5 Compliance posture (Discovery Gap)

- **GDPR**: no explicit data-subject-rights endpoint detected. Required when EU customers onboard.
- **SOC 2**: Supabase is SOC 2 certified; Bunkai itself unclear.
- **HIPAA**: Discovery Gap — healthtech segment listed but no BAA path documented.

### 3.3 Failure modes documented in code

| Failure | Detected where | Behavior |
|---|---|---|
| Supabase Auth 429 | `<target>/app/api/v1/auth/magic-link/route.ts` | Mapped to `rate_limited` envelope, HTTP 429 |
| Supabase Auth non-429 error | Same file | Mapped to `upstream_error` envelope, HTTP 502 |
| Invalid request body JSON | All Route Handlers | `bad_request` envelope, HTTP 400 |
| Zod validation failure | `withApiHandler` wrapper | `validation_failed` envelope, HTTP 422, with `details: issues[]` |
| RLS-denied row read | Supabase client returns `data: null` + `error` | Maps to `not_found` (404) in `DELETE /api/v1/tokens/[id]` |
| Postgres CHECK violation | Supabase error pass-through | Bubbles to `internal_error` (500) unless route catches |
| `bunkai_bootstrap_workspace` `42501` | RPC raises | Maps to `not_authenticated` — but Route Handler not yet checked-in for workspace POST |
| `bunkai_bootstrap_workspace` `22023` | RPC raises (invalid slug/name) | Maps to `validation_failed` (planned) |

### 3.4 Failure-mode test plan

| Test | Method | Pass criteria |
|---|---|---|
| Magic-link rate-limit | Hit `/api/v1/auth/magic-link` 50× in 1 min | 429 + `rate_limited` envelope after Supabase threshold |
| Service-role bypass attempt | Use anon key to insert into `access_tokens` with arbitrary `user_id` | RLS denies; row not inserted |
| Cross-workspace ATC read | User A's PAT (Phase F) attempts to read User B's ATC | 403 / 404; no data leaked |
| Idempotency replay | Same `idempotency-key` on planned `POST /api/v1/runs` → identical Run | **Gap until Phase F persistence lands** |
| Cookie tampering | Modify Supabase session cookie | Middleware redirects to `/login` |

## 4. Scalability

### 4.1 Multi-tenancy boundary

- **Workspace** is the tenant boundary. Every business-data row resolves to a `workspace_id`.
- **Materialized `modules.path`** (slash-separated) + GIN indices on `atcs.tsv` and standard FK indices keep tenant-scoped queries O(log n).
- **`modules` depth cap 6** prevents recursive-CTE fan-out blow-up (BR-008).

### 4.2 Connection pool

- Default Supabase pooler — bounded. Single-region today (`webapp_domain: upexbunkai.vercel.app` implies one Vercel region).
- Multi-region read replicas: out of MVP scope.

### 4.3 Hot paths

- ATC list per project: `atcs_project_id_idx` covers.
- ATC search: `atcs_tsv_gin_idx` covers (`@@` text search).
- Workspace membership check (every RLS): helper functions are SECURITY DEFINER STABLE — Postgres can cache per-statement.

### 4.4 Scaling assumptions (Discovery Gap)

- Largest tenant cardinality: unknown.
- Largest module tree: unknown beyond `depth ≤ 6`.
- Concurrent Runs per tenant: undefined (Run entity not migrated).
